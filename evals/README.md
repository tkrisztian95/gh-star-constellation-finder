# `evals/` — retrieval eval fixtures

Committed, frozen test data for the retrieval eval harness. `bun run evals` searches this data and grades the result — see the [Retrieval Evals](../README.md#-retrieval-evals) section of the root README for the why and the metrics.

Everything here runs **offline**: no GitHub token, no AI backend, no network. The data is committed precisely so the score is reproducible (and CI-gateable).

## Files

| File | What it is | Who writes it |
| --- | --- | --- |
| `repos.json` | Curated list of `owner/name` public repos — the input to the corpus builder. | Human (edit to add/remove repos) |
| `corpus.json` | `{ meta, entries }`. `meta` records provenance (`model`, `generatedAt`); each entry is frozen analyzer output (`owner`, `name`, `topics`, `category`, `killerFeature`, `description`, `isArchived`). The **haystack** search digs through. | Generated by `bun run evals:build-corpus` |
| `queries.json` | Hand-authored questions, each with one or more ground-truth repo URLs. The **test**. | Human |
| `baseline.json` | The scorecard today's keyword retriever achieves over this corpus + queryset. Carries `retriever` (which retriever produced it) but **no timestamp** — git records when, and a date would churn every run. The **floor** a smarter retriever (#44) must beat. | Generated by `bun run evals` |

> **Why provenance lives on the corpus, not the scorecard:** the corpus is what a model wrote, so "which model + when" is real, stable provenance (it's regenerated rarely). The scorecard must stay byte-reproducible for the `--check` gate, so it gets a deterministic `retriever` name but never a date.

## Add or change a golden query (single PR, no code)

1. Edit `queries.json`. Each entry:
   ```json
   {
     "question": "rust command-line tool that searches file contents",
     "expected": ["github.com/BurntSushi/ripgrep"],
     "style": "exact-recall"
   }
   ```
   - `expected` is one or more repo URLs (`github.com/<owner>/<name>`). **Every URL must already exist in `corpus.json`** — the harness fails fast and names any dangling reference.
   - `style` (optional, documentation only): `exact-recall` · `categorical` · `property-based` · `logical` · `health-check`.
2. Run `bun run evals` to refresh `baseline.json`.
3. Commit both files.

## Refresh the corpus (needs secrets)

To re-analyze repos or add new ones:

1. Edit `repos.json`.
2. `bun run evals:build-corpus` — requires `GITHUB_TOKEN` and an AI backend (`--backend ollama` or OpenAI). Fetches public metadata + README per repo and runs the real analyzer, rewriting `corpus.json`.
3. `bun run evals` to refresh `baseline.json`.
4. Commit `repos.json`, `corpus.json`, and `baseline.json` together.

> Refreshing the corpus changes the haystack, so existing query scores can shift — always re-commit `baseline.json` in the same PR. The CI `evals --check` gate fails if the committed baseline no longer reproduces.

## How retrieval works today (no model at query time)

There are two stages, and a model touches only the first:

```
STAGE 1 — corpus generation (runs ONCE, then frozen)
  an AI model reads each repo and writes its category / killerFeature /
  description. That output is frozen into corpus.json. The model's
  "knowledge" survives only as those frozen index cards.

STAGE 2 — answering queries (every `bun run evals`, NO model)
  query → split into words → count overlap against each repo's frozen
  text → rank → top-k. Pure keyword matching. No embeddings, no AI.
```

So the current harness is **not** a model answering questions. It grades a
dumb keyword matcher over frozen, model-written text — which means the score
partly reflects how good the frozen descriptions are and partly the floor-level
dumbness of lexical search. A query like _"execute models on my laptop"_ likely
**misses** `ollama` because no words overlap, even though the meaning matches.

Closing that meaning gap is the job of the embeddings retriever (#44). The
current keyword score is the **floor it must beat**.

## Git flow — how progress is tracked

Every change here lands on `main` through a branch → PR → merge, like the rest
of the repo. **Never commit a regenerated scorecard straight to `main`** — it is
a reviewable change. Always commit the fixture and its regenerated scorecard
**in the same commit**, so the diff shows what moved the numbers.

```
1. branch from main
2. make the change (queries / corpus / a new retriever)
3. bun run evals          # regenerate the scorecard
4. commit fixture + scorecard together
5. PR — review whether the numbers moved as expected — merge to main
```

| Change | Regenerate with | Commit together |
| --- | --- | --- |
| Add/edit queries | `bun run evals` | `queries.json` + `baseline.json` |
| Refresh/grow corpus | `evals:build-corpus`, then `bun run evals` | `repos.json` + `corpus.json` + `baseline.json` |
| New/better retriever (#44) | `bun run evals` | retriever code + its scorecard |

### Floor vs. current-best (relevant once #44 lands)

Today there is one retriever (keyword), so `baseline.json` is simply its score.
When a model-driven retriever arrives (#44), `baseline.json` keeps its meaning as
the **frozen keyword floor**, and the model retriever gets its **own** committed
scorecard that ratchets upward as retrieval improves. `main` holds both; the
climbing model score, visible in git history, is the progress signal.

### CI gate caveat

CI runs `bun run evals --check`, asserting the produced scorecard **reproduces**
the committed one exactly. This works because the keyword retriever is
deterministic. A model retriever may not be:

- embeddings with a pinned model → usually deterministic → exact `--check` still works.
- an LLM answering with temperature → non-deterministic → exact match fails.

So when a non-deterministic retriever is scored, the gate must shift from
_exact-reproduce_ to a **threshold** (`score >= committed − ε`, a regression
catch) rather than exact equality. That change belongs to #44, not the current
keyword harness.

## Coverage notes

- The corpus is curated **public** repos so query authors share a stable, recognizable haystack — it is not anyone's personal stars.
- Query styles span exact-recall, categorical, property-based, logical (AND/OR/negation), and health-check, across lengths from 1–2 word terms to long natural-language sentences.
- Health-check coverage is currently thin: only one corpus repo is archived. Add more archived repos to `repos.json` to strengthen it.
