## Context

GitHub enforces a hard cap of **32 lists** per account. The app's AI pipeline has two phases:

1. **Per-repo analysis** (`openaiAnalyzer` / `ollamaAnalyzer`) — already receives existing list names via `buildSystemPrompt` to encourage reuse.
2. **Consolidation** (`consolidator.ts` + `buildConsolidationPrompt`) — receives only the *proposed new names* from the analysis phase; it has no knowledge of existing lists or the 32-list budget.

When a user with, say, 28 existing lists runs analysis on a batch of untagged repos, the consolidator may still output 10 distinct new categories, driving the total to 38 — all `create-list` mutations beyond the 32nd silently fail.

## Goals / Non-Goals

**Goals:**
- Consolidation prompt knows: (a) existing list names, (b) total existing count, (c) the 32-list hard cap.
- Consolidator actively merges proposed categories to keep `existing + new ≤ 32`.
- When merging occurs, the user sees a clear advisory listing what was collapsed and why, so they can review or override.
- Architectural change is minimal: thread existing list data down to the consolidator.

**Non-Goals:**
- Automatic deletion or renaming of *existing* lists to free up slots.
- Surfacing the 32-list limit before analysis starts (a future UX concern).
- Changing the per-repo analysis phase (it already reuses existing list names).

## Decisions

### 1 — Extend `buildConsolidationPrompt` to accept existing context

`buildConsolidationPrompt(proposedNames)` becomes:

```ts
buildConsolidationPrompt(
  proposedNames: string[],
  existingListNames: string[],
  maxLists: number = 32
): string
```

**Rationale:** The prompt is the single authoritative place to express the constraint. Encoding it there means both OpenAI and Ollama backends benefit without any backend-specific changes.

**Alternative considered:** Apply a post-processing cap in the consolidator (truncate or merge the weakest new categories programmatically). Rejected — the AI can make semantically better merge decisions than a purely mechanical cut.

### 2 — Bubble existing list names up to consolidator callers

`consolidateCategories` gains a second parameter:

```ts
consolidateCategories(
  proposedNames: string[],
  existingListNames: string[]
): Promise<Map<string, string>>
```

The orchestration layer (wherever `consolidateCategories` is called today) already has access to `existingLists: GitHubList[]` — it just needs to pass `existingLists.map(l => l.name)`.

### 3 — Return merge advisory alongside the remapping

`consolidateCategories` currently returns `Map<string, string>`. Extend the return type to:

```ts
interface ConsolidationResult {
  remapping: Map<string, string>;
  mergeWarnings: string[];  // human-readable advisories, empty when no budget pressure
}
```

`mergeWarnings` entries are generated by comparing the pre/post names and flagging any that changed. The UI layer renders these as a yellow advisory block.

**Alternative considered:** Log warnings inside the consolidator. Rejected — the UI layer needs structured data to render them properly; side-channel logging loses context.

### 4 — Prompt budget instruction

The consolidation prompt gains a `LIST BUDGET` section:

```
LIST BUDGET
The developer already has {existingCount} lists. GitHub enforces a hard limit of {maxLists} lists.
You may create at most {budget} new list names (= {maxLists} − {existingCount}).
If the proposed names would exceed this budget, merge the least-specific categories into broader ones.
Prefer merging new proposals over inventing vague umbrella names. When you merge, prefer the more specific surviving name.
The existing list names are listed below — do NOT create a new name that is semantically identical to one of them.
EXISTING LISTS:
{existingListNames}
```

## Risks / Trade-offs

- **LLM non-compliance** — The model may ignore the budget instruction and still emit more names than allowed. Mitigation: add a post-processing guard in `consolidateCategories`: if `(existingCount + distinctNewNames) > maxLists`, programmatically merge the least-represented new names (fewest repos) into the most-popular new name as a fallback.
- **Quality degradation on tight budgets** — If a user has 31 existing lists, the AI must collapse all new proposals into 1 name, which may be too generic. Mitigation: the merge advisory tells the user exactly what happened so they can manually delete old lists before rerunning.
- **Breaking change in consolidator API** — Any caller of `consolidateCategories` or `buildConsolidationPrompt` must be updated. Mitigation: the codebase is small; a single call site exists in `consolidator.ts` and one upstream caller in the orchestration layer.

## Migration Plan

1. Update `buildConsolidationPrompt` signature and prompt template.
2. Update `consolidateViaOpenAI` and `consolidateViaOllama` to pass the new parameters and return `ConsolidationResult`.
3. Update `consolidateCategories` signature and return type.
4. Update the orchestration caller to pass `existingListNames` and handle `mergeWarnings`.
5. Update the UI layer to render merge advisories.
6. Update unit tests for the prompt builder and consolidator.

No migration of stored data is needed — this is a pure runtime behaviour change.

## Open Questions

- Should the post-processing fallback (LLM non-compliance guard) be a hard error or a silent clamp? Leaning toward silent clamp with an extra warning entry.
- Is the advisory shown inline in the suggestions list, or as a banner before it? TBD with the TUI layer.
